# プロンプトに含めるデータのサンプル(PromptPayload)

[design.md](design.md) の「Javaクラス構成」で触れた `PromptSnapshotSelector` が生成し、OpenAIへのユーザーメッセージとしてそのままJSON化して渡す想定のデータ(`PromptPayload`)のサンプル。実データ([sample/slimerace7.json](sample/slimerace7.json)、スライムレース第7回)から実際に抽出した値を使用している。

**この設計は、以前検討していた「Java側で4分析軸(ボーダー推移/順位変動/勢い/新規・圏外)を事前集計する」方式を破棄した後のもの。** 順位変動・勢い・新規ランクイン/圏外落ちの判定・計算はJavaでは行わず、この生に近いデータをそのままOpenAIに渡して分析させる。

## データ選別ルール

- 直近5スナップショットを対象にする
- 各スナップショットについて、以下の順位の`RankItem`のみを残す(それ以外は除外)
  - **各ボーダー([border.md](border.md) 参照)の前後20位**(追跡順位数でクランプ)を統合(重複除去)する。「1〜15位を必ず含める」という別枠の条件は設けない。いずれのレースも10位ボーダーを持つため、その前後20位ウィンドウ(最大30位まで)が1〜15位を自動的にカバーする(例: 1位ボーダーは最大21位まで、10位ボーダーは最大30位まで対象になる)
- 順位変動・勢い・新規ランクイン/圏外落ちの判定はしない。ほぼ生の`RankItem`(rank/point/name/id)を渡すのみ

## サンプルのデータ量

このサンプルは`slimerace`(ボーダー: 1位/10位/100位、追跡順位数100)のケース。

- 1位ボーダーの前後20位ウィンドウ: 1〜21位
- 10位ボーダーの前後20位ウィンドウ: 1〜30位(10-20は0以下のため1にクランプ)
- 100位ボーダーの前後20位ウィンドウ: 80〜120位 → 追跡順位数の上限(100位)でクランプされ80〜100位

これらを統合すると、実際に抽出される範囲は**1〜30位、80〜100位**になる(「1〜15位を必ず含める」という別枠の条件がなくても、10位ボーダーのウィンドウにより1〜15位は自動的にカバーされる)。

| 項目 | 値 |
|---|---|
| 1スナップショットあたりの件数 | 51件(1〜30位: 30件 + 80〜100位: 21件) |
| 5スナップショット合計 | 255件 |
| コンパクトJSON文字数 | 13,657文字 |
| 概算トークン数 | 約5,400トークン(`tiktoken`の`o200k_base`エンコーディングで実測) |

fishing/daifugo/daifugom/pencilのようにボーダーが100位・200位・1000位を含むレースでは、1〜30位(30件)に加えて100位ウィンドウ(80〜120位、41件)、200位/1000位ウィンドウ(追跡順位数の上限でクランプされ21件程度)が加わり、1スナップショットあたり最大92件になる見込み。詳細な比較は [design.md](design.md) の「入力トークン量の見積もり・モデル選定」を参照。
