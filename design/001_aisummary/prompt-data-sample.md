# プロンプトに含めるデータのサンプル(PromptPayload)

[design.md](design.md) の「Javaクラス構成」で触れた `PromptSnapshotSelector` が生成し、OpenAIへのユーザーメッセージとしてそのままJSON化して渡す想定のデータ(`PromptPayload`)のサンプル。実データ([sample/slimerace7.json](sample/slimerace7.json)、スライムレース第7回)から実際に抽出した値を使用している。

**この設計は、以前検討していた「Java側で4分析軸(ボーダー推移/順位変動/勢い/新規・圏外)を事前集計する」方式を破棄した後のもの。** 順位変動・勢い・新規ランクイン/圏外落ちの判定・計算はJavaでは行わず、この生に近いデータをそのままOpenAIに渡して分析させる。

## データ選別ルール

- 直近5スナップショットを対象にする
- 各スナップショットについて、以下の順位の`RankItem`のみを残す(それ以外は除外)
  - **1〜15位は必ず含める**
  - **各ボーダー([border.md](border.md) 参照)の前後10位**(ボーダーが1〜15位に含まれる場合は対象外。例えば10位ボーダーは1〜15位に含まれるため追加のウィンドウは不要)
- 順位変動・勢い・新規ランクイン/圏外落ちの判定はしない。ほぼ生の`RankItem`(rank/point/name/id)を渡すのみ

## サンプルのデータ量

このサンプルは`slimerace`(ボーダー: 1位/10位/100位、追跡順位数100)のケース。100位ボーダーの前後10位ウィンドウ(90〜110位)は、追跡順位数の上限(100位)でクランプされるため実際は90〜100位の11件になる。

| 項目 | 値 |
|---|---|
| 1スナップショットあたりの件数 | 26件(1〜15位: 15件 + 90〜100位: 11件) |
| 5スナップショット合計 | 130件 |
| コンパクトJSON文字数 | 7,076文字 |
| 概算トークン数 | 約2,400〜3,500トークン |

fishing/daifugo/daifugom/pencilのようにボーダーが100位・200位・1000位を含むレースでは、1スナップショットあたり最大47件(1〜15位: 15件 + 100位ウィンドウ: 21件 + 200位/1000位ウィンドウ: 追跡順位数の上限でクランプされ11件程度)になる見込み。詳細な比較は [design.md](design.md) の「入力トークン量の見積もり・モデル選定」を参照。

## このデータからOpenAIが行う分析(参考)

このデータ自体には分析結果は含まれていない。以下はOpenAI側が計算すべき内容の例(実際の出力はプロンプトの指示次第):

- 1位(id=0)の`point`が2024-01-21T04:00以降4スナップショット連続で600,000,000のまま変化していない → 得点上限到達・足踏みの検出
- 90〜100位の各スナップショットの先頭(このサンプルでは90位)にいるプレイヤーIDが毎回異なる(id=1→176→173→201→201) → 100位ボーダー付近の激しい入れ替わりの検出
- 90位の直近5スナップショットの`point`推移(96,185,000 → 100,255,000 → 100,275,000 → 103,050,000 → 106,325,000)からペースを計算 → 終盤の着地予想
